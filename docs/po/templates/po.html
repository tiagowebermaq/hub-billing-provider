2. Visão do produto

O Hub Billing Provider é um serviço central que coleta, normaliza e agrupa as contas recorrentes de consumo (energia elétrica e água) dos imóveis administrados, vincula cada conta ao imóvel e ao contrato de locação correspondente e entrega essas contas, de forma confiável e rastreável, ao sistema de aluguéis.

O hub também expõe uma API REST e emite webhooks para que outros sistemas, acoplados no futuro, consumam os mesmos dados sem integração direta com as concessionárias.

Declaração de visão: para administradores de imóveis que precisam repassar contas de consumo aos contratos de locação, o Hub Billing Provider é a fonte única e auditável de contas de energia e água, que elimina a coleta manual por concessionária e entrega as contas prontas para cobrança.

3. Problema, objetivos e métricas de sucesso

3.1 Problema

  • Cada concessionária (CPFL/RGE, Aegea/Corsan) tem portal, formato e calendário próprios.
  • A coleta manual é lenta, sujeita a erro e não deixa trilha de auditoria.
  • O sistema de aluguéis precisa receber as contas já vinculadas ao imóvel/contrato, sem duplicidade.

3.2 Objetivos

  • Automatizar a coleta de 100% das contas dos imóveis cadastrados nos provedores suportados.
  • Agrupar as contas por imóvel, contrato e competência (mês de referência).
  • Entregar as contas ao sistema de aluguéis com garantia de entrega e idempotência.
  • Disponibilizar API e webhooks para novos sistemas consumidores.
  • Permitir adicionar uma nova concessionária criando apenas um novo adapter.

3.3 Métricas de sucesso (KPIs)

4. Escopo

Dentro do escopo (v1)

  • Cadastro de imóveis, unidades consumidoras (energia) e matrículas (água).
  • Cadastro de credenciais de acesso por provedor, armazenadas cifradas.
  • Coleta agendada e sob demanda via adapters CPFL/RGE e Aegea/Corsan.
  • Normalização para o modelo canônico de conta.
  • Agrupamento por imóvel / contrato / competência.
  • Envio ao sistema de aluguéis.
  • API REST, webhooks assinados e painel de administração.
  • Conta admin e usuários com permissões concedidas pelo admin.
  • Logs estruturados com Correlation ID e auditoria.
  • Docker Compose; execução em Windows e Ubuntu.

Fora do escopo (v1)

  • Pagamento das contas pelo hub.
  • Cobrança ao inquilino (responsabilidade do sistema de aluguéis).
  • Outras utilidades (gás, internet, condomínio), previstas para versões futuras.
  • Aplicativo mobile.
  • OCR avançado de contas digitalizadas em papel.

10.3 Regras do Correlation ID

  • Gerado na entrada do fluxo (API, scheduler ou upload) se não vier no cabeçalho X-Correlation-ID.
  • Copiado para a propriedade AMQP correlation_id e para o envelope de todas as mensagens derivadas.
  • Incluído em todos os logs (via contextvars), registros de auditoria, chamadas ao sistema de aluguéis e webhooks.
  • Retornado no cabeçalho de resposta da API, permitindo rastrear uma conta de ponta a ponta.

10.4 Idempotência

  • Chave de negócio da conta: provider + account_id + reference_month (único no banco).
  • Chave de mensagem: message_id gravado no Redis com TTL; mensagens repetidas recebem ack sem reprocessar.
  • Envio ao sistema de aluguéis usa cabeçalho Idempotency-Key = ID do lote.

11. Padrão Adapter de provedores

Cada concessionária é implementada como um adapter que obedece a uma interface única. O restante do hub nunca conhece detalhes do provedor. Adapters são registrados por nome e habilitados por configuração.

class ProviderAdapter(Protocol):
    code: str                       # "cpfl", "aegea"
    utility_type: UtilityType       # ENERGY | WATER

    async def authenticate(self, credentials: ProviderCredentials) -> Session: ...
    async def list_accounts(self, session: Session) -> list[ProviderAccount]: ...
    async def fetch_bills(self, session: Session, account: ProviderAccount,
                          reference: YearMonth | None = None) -> list[RawBill]: ...
    async def download_document(self, session: Session, bill: RawBill) -> bytes: ...
    def to_canonical(self, raw: RawBill) -> Bill: ...
  • Registro: AdapterRegistry.register("cpfl", CpflAdapter); novos provedores entram sem alterar o núcleo.
  • Variações: distribuidoras/unidades (ex.: RGE, Corsan) são parâmetros do adapter, não novos adapters.
  • Resiliência: timeout, retry com backoff, circuit breaker e rate limit (Redis) por provedor.
  • Testabilidade: cada adapter possui um FakeAdapter e fixtures de respostas reais anonimizadas.

13.3 Contrato de entrega

  • Cabeçalhos: X-Hub-Event, X-Hub-Delivery, X-Correlation-ID, X-Hub-Timestamp, X-Hub-Signature-256 (HMAC-SHA256 de timestamp.body).
  • Sucesso = HTTP 2xx em até 10 s. Caso contrário, retentativas em 30 s, 5 min, 1 h, 6 h e 24 h; depois DLQ e alerta.
  • Consumidores devem ser idempotentes usando X-Hub-Delivery.

13.4 Integração com o sistema de aluguéis

Modo padrão: o hub faz POST do lote para a API do sistema de aluguéis com Idempotency-Key. Modo alternativo: o sistema de aluguéis assina o webhook batch.ready ou consulta GET /batches. O contrato exato será definido com o time do sistema de aluguéis (questão em aberto Q-01).

14. Segurança, usuários e permissões

Controle de acesso baseado em perfis (RBAC) com permissões granulares. A conta admin possui todas as permissões e é a única que pode conceder permissões a outros usuários.

PermissãoAdminOperadorConsulta
users:manage, roles:manage✔––
providers:credentials:write✔conforme admin–
properties:write, accounts:write✔✔–
collections:run, batches:resend✔✔–
bills:read, batches:read✔✔✔
webhooks:manage, api-clients:manage✔conforme admin–
audit:read✔conforme admin–
  • Toda ação de escrita é registrada na auditoria com o Correlation ID.
  • Bloqueio após tentativas de login inválidas (rate limit no Redis).
  • Chaves de API de sistemas acoplados com escopos e expiração; rotação pelo admin.

17. Política de versionamento do PO

  • Versionamento semântico do documento: MAJOR.MINOR.PATCH.
    • MAJOR: mudança de visão, escopo ou arquitetura que quebra o acordado.
    • MINOR: novo requisito, provedor, evento ou épico.
    • PATCH: correções de texto, esclarecimentos, ajustes de prioridade.
  • Toda alteração gera novo PDF e novo infográfico: docs/po/vX.Y.Z/PO_Hub_Billing_Provider_vX.Y.Z.pdf e Infografico_Hub_Billing_Provider_vX.Y.Z.(pdf|png). Versões anteriores nunca são sobrescritas.
  • O arquivo docs/po/VERSION guarda a versão atual e docs/po/CHANGELOG.md o histórico (também impresso na seção 1).
  • Geração: python tools/build_po.py --bump minor -m "descrição" (funciona em Windows e Ubuntu).
  • Os artefatos são salvos no PC (pasta local do projeto) e no GitHub (commit + tag po-vX.Y.Z).

Concessionária sem API oficial; portal muda layout ou usa captchaAltoAdapter isolado, testes com fixtures, alerta de falha, upload manual como contingência, buscar convênio/EDI.
Termos de uso dos portais restringem automaçãoAltoValidação jurídica na E1; priorizar canais oficiais (API, e-mail de fatura, EDI).
Credenciais de clientes vazadasAltoCifragem, segredos fora do código, acesso restrito por permissão, auditoria.
Contrato da API do sistema de aluguéis indefinidoMédioDispatcher com adapter próprio; modo webhook/pull como alternativa.
Diferenças Windows × UbuntuBaixoDocker como padrão, CI nas duas plataformas.

19.2 Premissas

  • Os imóveis e contratos já existem no sistema de aluguéis e têm um ID externo estável.
  • O titular das contas autoriza o acesso às faturas (LGPD).
